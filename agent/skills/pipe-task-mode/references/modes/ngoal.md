# ngoal —— 目标驱动迭代模式

首词是 `ngoal` 时使用本文件。重点只有两件：**先把「完成」定义清楚**，然后**用回合制逼近到全绿**。判据从红变绿必须是**实测结果**，不能是阅读代码后的推论。本文件自包含：范围、上下文、验证、收尾、阻塞与失败的判定都在这里。

用户用 `ngoal` 开头就是在说：**别问我、别报回合预算，直接做到能验收为止。**

本文件是 `ngoal` 模式的**唯一规则来源**。执行时不参照、不援引任何其它模式文件；与本文件冲突的其它约定一律以本文件为准。

---

## 一、入口与需求理解

收到 `ngoal <需求>` 后，**先不要动手改任何代码或文件**。第一步是把需求读懂并定型。

1. **拆解需求**：把用户原话拆成若干条可辨认的诉求。原话有歧义、有隐含前提、有多种合理读法的，逐一列出。
2. **收敛到最终意图**：对每条歧义自行选定一种读法，并写明选它的理由。**不要为了确认读法而停下来问用户**——按「尽量自动决策」处理，先选定并记档，用户看到记录后仍可否决。
3. **界定边界**：明确本次交付**包含**什么、**不包含**什么。不包含的部分若与需求相关，写成「不纳入本次目标，理由：…」。
4. **定出验收判据**：把「完成」写成一组可执行、可观测的检查项。每条判据必须能在本机真实跑出结果（命令 + 预期输出 / 断言 / 文件状态），不接受「读代码看是对的」这类推论，也不接受「应该没问题」这类模糊表述。

## 二、临时文档

理解结果与全程状态都写进**临时目录下的 md 文档**，作为本次交付的唯一事实来源。

- 路径：临时目录（系统临时目录或项目内一次性的临时路径）下，文件名体现本次目标，如 `<temp>/ngoal-<目标简述>.md`。
- 目录不存在先创建；同一目标复用同一份文档，不要每回合新开文件。
- 文档是**活文档**：每回合结束后就地更新，不要只在脑子里推进。
- 文档在验证全部通过前**不得删除**；删除时机见「六、收尾」。

文档必须包含以下小节：

```markdown
# ngoal: <目标简述>

## 需求原话
<用户原话，不改写>

## 最终意图
<收敛后的一句话目标>

## 拆解与读法决策
| 诉求 | 歧义点 | 选定读法 | 理由 |

## 边界
- 包含：…
- 不包含：…（理由）

## 验收判据
| 编号 | 检查项 | 如何实测（命令/断言） | 预期结果 | 状态 |

```

**「验收判据」的状态列只允许 `待验 / 绿 / 红`**，由实测结果改写，不允许预填 `绿`。

## 三、回合制迭代

理解定型后，从**回合 1** 开始按回合推进，直到全部判据为绿。

每回合的固定流程：

1. **报告标题**：每回合一开头就输出标题，格式为
   `G<N> —— <本回合临时目标>`
   其中 `G<N>` 表示第 N 回合：`G1` 是第一回合，`G3` 是第三回合。N 从 1 起连续递增，不回退、不跳号。
   例：`G3 —— 让重启后续写落到最后一段`。
2. **定临时目标**：制定单回合目标与验证标准，目标过大就拆到后续回合。
3. **动手**：完成本回合所需的修改 / 命令。
4. **实测验证**：验证单回合验证标准，只测本回合变更的内容。
5. **报告变更**：更新判据状态与回合记录（本回合做了什么、验证输出、结果），报告最终目标临时文档路径。
6. **安排下回合**：根据本回合完成的内容，规划下回合待办，明确写出下回合的标题与临时目标。

约束：

- **不虚报回合**：回合计数如实递增，一个回合内不做多轮「隐形回合」。
- **失败回合也算一回合**：红就如实记红，写清失败输出，下一回合修正；不要重写编号抹掉这次失败。

## 四、自动决策

本模式默认**自动决策，不提问**。遇到以下情形自行决断并记入文档：

- 需求歧义 → 选代价小、可回退、与项目既有约定一致的那种读法。
- 实现路径有多条 → 选改动面小、验证成本低的那条。
- 判据在原环境下无法精确测量 → 换成可测的等价观测（写清等价理由）。
- 需要新增依赖 / 改公共接口 → 先评估影响，影响可控则做，并记入「边界」。

## 五、中止

出现**外因导致无法继续**的条件时，立即中止，不做无谓重试、不假装完成。中止时：

1. 文档保留（**不删除**）。
2. 输出中止报告：`中止 —— G<N>`，然后说明
   - 卡在哪条判据 / 哪种检查；
   - 外因是什么（缺凭据、缺环境、缺权限、依赖服务不可达、用户需现场操作、判据自相矛盾等）；
   - 已经完成且实测为绿的部分；

外因清单（命中即中止，不重试、不绕路）：

- 缺少必要的凭据 / 密钥 / 权限。
- 缺少运行环境（服务、数据库、设备、网络）且本机无法自建。
- 需求内部矛盾，任何读法都无法同时满足判据。
- 继续操作会造成不可逆破坏（删数据、改生产、强推远端等）且无授权。
- 判据无法实测且不存在等价观测。

**不中止**的情形：测试失败、编译报错、实现比预想复杂、单回合目标没做完——这些是正常迭代内容，下一回合继续。

## 六、收尾

全部判据实测为绿后，按以下顺序收尾：

1. **按文档跑全量验证**：回到文档「验收判据」表，从第一条到最后一条**逐条重跑**。不要挑着跑，不要复用回合内的旧输出。
2. **确认全绿**：任何一条复跑为红 → 不算完成，回到回合制，另起回合修，修完再做一次全量复跑。
3. **删除临时文档**：全量验证确认全绿后，删除 `<temp>/ngoal-<目标简述>.md`（含本目标创建的任何临时文件）。
4. **总结汇报**：输出
   - 最终意图与达成情况；
   - 逐条判据的复跑结果（绿）；
   - 共用了多少回合、每回合做了什么（一句话一条）；
   - 实际改动的文件清单；
   - 边界外未做的事与理由；
   - 若过程中有过被中止的风险或值得注意的取舍，一并说明。

**顺序不可颠倒**：先全量验证，再删文档，最后汇报。删除之前不得宣布完成；汇报里若提到判据结果，必须是复跑输出。

## 七、反模式

- 读完需求就开干，没有定下可实测的验收判据。
- 判据写成「功能正常」「代码质量好」这类无法实测的表述。
- 把「读代码后推断正确」当作验证通过。
- 全量验证没跑就删掉临时文档。
- 回合标题缺失 / 回合编号注水（把失败的回合改号抹掉）。
- 回合编号写成 `回合 3`、`R3`、`第 3 回合` 等其它形式——只用 `G3`。
- 本可以自动决断的歧义却停下来问用户。
- 遇到外因卡点不中止，反复空转重试。

## 八、例子

> 用户：`ngoal 让 wrun 的命令日志按段淘汰也能在重启后正确续写`

拆解后可能收敛为：意图 = 段文件名有序且重启后 append 进正确段；边界 = 不改全局淘汰阈值、不动合并逻辑；判据 = ①造 3 段后重启，新输出落最后一段且行序连续（实测：脚本 + 读文件比对）②手写连接级测试通过（实测：`npm test -- durability`）。文档落 `<temp>/ngoal-log-segment-resume.md`。

回合标题示例：`G1 —— 让重启后续写落到最后一段`。
