# nplan —— 计划预算模式

首词是 `nplan` 时使用本文件：先说清要跑几轮，再严格跑这么多轮——范围被钉死，轮次可核对。本文件自包含。

## 0. 验证类请求

**验证类请求**：请求主句是「测试 / 验证 / 检查 / 看看有没有问题 / 跑一遍看正常不正常」时，交付物是**结论**——判据写成「给出结论」，发现缺陷只报现象、位置、原因、建议改法，**不动业务文件**（`src/`、`packages/` 等），除非用户原话说了「有问题就直接修」。这类请求的判据就是报告本身：报告成形即算达成该轮判据，不要求 §1 的验证动作；但报告里每条结论都必须有实测输出或代码位置支撑。

这类请求最多 2 轮：R1 取证、R2 下结论；只做一件事时可退化为 N=1，判据为「给出结论」。

## 1. 范围、上下文与验证

**范围：请求没提的不碰。** 请求 / 判据没要求、只是看起来顺路的，一律**不做**，写进收尾的 `后续:`：

**上下文：只信本会话。** 依据的「已有状态」只能来自本次会话里用户说过的话、本会话亲手读过的文件、刚跑出来的输出。父目录 / 兄弟目录里别人的产出、别的会话文件、stash 里的半成品、git 里未提交的陌生改动、README TODO、以及自己对「之前应该做过什么」的推测都不可信。

**验证：没验成就不能打 `✓`。** 算一次验证：跑测试、跑目标命令看输出、语法 / 类型检查、开工具确认结果、写临时脚本复现。不算验证：读文件、搜索、看报错信息——那些是获取信息。同一手段失败两次就换思路（换入口、缩小范围、先写最小复现），不是加力度。

## 2. 一个工作轮是什么

工作轮 = 一次有明确完成判据的推进：**宣布 → 执行 → 一行结果**。默认在一次回复内连续跑完所有轮次。

**一个工作轮最多做两次验证：改完跑一次，修完复验一次。** 这是硬限，什么算一次验证见 §1。

按验证结果处理：

| 情况 | 处理 |
| --- | --- |
| 验证通过（只跑一次就绿也算） | 该轮完成，写 `✓` |
| 第二次失败，但**失败出在验证手段本身**（脚本笔误、命令写错） | 改动保留，收尾标 `◑ k/N`（k = 已完成的轮数），`后续: 补验 <什么>`。不许打 `✓` |
| 失败是因为**环境不对**（缺服务、缺凭据、缺机器） | 按 §5 的阻塞收尾，不再验证 |
| 两次都显示改动确实错了（额度已耗尽） | **该轮失败**：`✗ Rk/N 失败: <错在哪、已了解的原因>`，不得开第三次验证 |

**失败只终止当前轮。** 后续轮不依赖失败轮时继续 R(k+1)，并在该轮开头一行说明影响（「R2 失败，R3 不依赖它，继续」）。只有当后续轮全部依赖失败轮、或已无轮次可推进时，才 `✗ 整体失败: <哪几轮失败、卡在哪、从未执行的轮次>`。

需要多维度验证时拆成**多个工作轮**，每轮各带判据与自己的两次上限。全量测试套件只在请求涉及跨模块改动或用户明确要求时跑。

## 3. 出计划（动手之前，同一条回复里）

先写计划，再执行 R1：

```
PLAN <N> | <用自己的话一句话说清目标>
R1 <任务> → <完成判据>
R2 <任务> → <完成判据>
R3 <任务> → <完成判据>
```

- **N 默认 ≤ 5。** 真实需要更多时，只规划能产出可验证里程碑的前 ≤5 项，另起一行写 `剩余: <未排入的项>`。
- **拆得动就拆**：含「以及/顺便/同时」的、需要两种不同验证方式的、跨不同文件且要分别验证的，都是两个任务。
- **拆不动就别拆**：一句话能改完的 N=1，计划退化成一行。
- **目标用自己的话压缩**，不要复述原文。理解没把握时，把它做成 N=1 的澄清轮，判据是用户确认目标。

## 4. 执行

每轮开头打一行进度：

```
▶ R2/3 <任务名>
```

然后干活，用最少的工具调用达成该轮判据；本轮结束时用一行写结果与缺口。

## 5. 收尾

| 状态 | 写法 |
| --- | --- |
| 全部完成且判据达成 | `✓ N/N <一句话结果>` +（有则 `后续:`） |
| 完成但没验成（验证手段可自修、两次额度已尽） | `◑ k/N <已完成的部分>（缺验证）` + `后续: 补验 <什么>` |
| 计划里写过 `剩余:` | `◑ N/N <已完成>（缺范围: <未排入项> 未做）` + `后续: <什么时候继续>`；不许只打 `✓ N/N` |
| 该轮失败（自己的错、额度已尽，后续还有独立轮次） | `✗ Rk/N 失败: <错在哪、已了解的原因>`，继续下一轮 |
| 整条计划失败 | `✗ 整体失败: <哪几轮失败、卡在哪、从未执行的轮次>` |

`✓` 只留给判据真的绿了的轮次；`◑` 的括号必须注明缺的是哪一项：验证 / 范围。

## 6. 生命周期

- **「继续」/「go on」**：从上一轮之后接着跑，N 与判据不变。本会话没有可续的上下文时。
- **修正或追加需求**：按本模式重出计划，旧计划作废，重算 N、R 从 1 重排。
- **换话题，或插入一件无关的事**：新的计划，从 R1 开始。
- **新消息开头换了模式词**：本模式的计划作废，剩余轮次不再补跑。

## 7. 例子

**验证类请求：给结论，不动手**

```
PLAN 2 | 实测 retry 的真实行为并给出结论（不改代码）
R1 写临时脚本复现 retry / uploadAll 行为 → 拿到实测输出
R2 对照源码得出「正常/不正常」的结论 → 每条结论都有实测或代码位置支撑
✓ 2/2 retry 本身次数与错误传递正常；问题在调用点：uploadAll 传的是 thunk，重试从未触发（src/pipeline.js:33）
后续: 建议改为 retry(items[index], ...) 并让 uploadAll 读 uploadConcurrency；要我改就说一声
```

## 8. 反模式

- **需要改文件却不写 PLAN**，或把「看看有没有问题」当成「改到没问题」——前者让轮次无法核对，后者交付的是既成事实而不是结论。
