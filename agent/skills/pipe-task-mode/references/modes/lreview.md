# lreview loop review 迭代审查修改

对「目标产出」做**多轮审查 → 修改 → 再审查**的闭环，直到达到收敛条件或达到轮次上限。

## 触发

用户消息以 `lreview` 开头，其后是审查目标（文件 / 目录 / 功能点 / 设计文档），可附带关注维度、轮次上限、验收标准。

```
lreview [ARGS]
```

- 未指定范围时按整个工程
- 未给轮次上限时默认 **5 轮**
- 未给维度时按「正确性 → 一致性 → 健壮性 → 可维护性 → 文档同步」顺序检查

## 轮次前的准备（只做一次）

1. **圈定范围**：明确本轮的审查文件/函数清单，范围外的顺手问题只记入「备忘」，不改。
2. **总结报告**：输出小结，不需要用户确认，直接进入迭代轮次。

## 单轮流程

每轮固定五步，**顺序不可颠倒**：

### 1. 审查（不写代码）
- 逐文件通读改动/目标范围，记录问题到清单，每条包含：位置、现象、影响、建议改法、严重度（阻断 / 重要 / 次要 / 建议）
- 必要时实际运行或写最小复现验证判断，禁止纯推测下结论

### 2. 归类与排序
- 阻断级（编译失败、用例红、接口不兼容、数据会丢）**必须本轮修完**
- 重要级本轮修，次要/建议级按剩余预算取舍，未修的显式列入「遗留」
- 同一根因的多条问题合并为一条「根因条目」，修一次

### 3. 修改
- 只改清单内条目，遵循项目既有风格与约定
- 一个文件多处改动合并为一次整写，减少半成品状态
- 改了行为就同步文档/测试，不留「代码改了文档没改」
- 每次修改立刻可验证，不做「攒一堆再跑」

### 4. 验证
- 对比确认差异自查
- 新增/改动的行为补对应用例
- 报告必须给出实际命令与实际输出摘要，禁止「应该没问题」

### 5. 记录
- 输出本轮小结：修了什么、跳了什么及理由、发现的新问题、下轮重点
- 更新剩余问题清单（已修项划掉而不是删除，保留轨迹）

## 收敛判定

满足任一条件即停止迭代：

| 条件 | 含义 |
| --- | --- |
| 清单清空 | 无阻断/重要项 |
| 无实质收益 | 新一轮仅发现措辞级、风格级问题 |
| 达到轮次上限 | 达到 N 轮 |
| 用户叫停 | 收到停止指令 |
| 决策中断 | 遇到需要用户决策的问题 |

**不收敛信号**（出现即改变策略，而不是继续原样轮回）：
- 连续两轮修 A 坏 B → 根因在架构/接口层，转为「先重构再修」
- 问题数量每轮不降 → 审查范围过大，切小范围重来
- 同一问题反复被判「重要」但始终未修 → 需求本身模糊，回到标准澄清

## 报告格式

```
## 第 N 轮
范围：<文件/模块>
发现：阻断 a / 重要 b / 次要 c / 建议 d
已修：<条目 → 改动位置>
未修：<条目 → 理由/遗留计划>
验证：<命令> → <结果摘要>
下轮重点：<...>

## 收尾
结论：收敛 / 未收敛（原因）
最终状态：<测试/构建/lint 结果>
遗留清单：<显式接受的次要项>
```

## 边界

- 不扩大到未授权范围：范围外问题只记录不修
- 不为了「清零问题」而删测试、放宽断言、吞异常、加 `any`/`# type: ignore`
- 不为通过审查而改需求；需求冲突先提问
- 完成标准是「可判别的证据」，不是「自我感觉良好」
- 涉及不可逆操作（删数据、强推远端、批量改名）前必须先确认
