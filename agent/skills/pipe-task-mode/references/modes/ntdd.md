# ntdd —— TDD 测试驱动模式

首词是 `ntdd` 时使用本文件。按 TDD 的本义交付：**先红、后绿、再重构**。

## 0. 范围与上下文

**范围：只做驱动当前行为所需的改动。** 请求没要求、只是看起来顺路的，一律不做，写进收尾的 `后续:`：行为变更、顺带重构、顺带补注释、顺带改文档、顺带加无关测试——哪怕你顺手看到了 bug。新建测试文件属于任务范围：**动手前先用一句话列出路径与用途**（`将创建: <路径> — <用途>`），再动手。

**无论请求怎么说，下列操作先问再动**：删除文件或目录；git 操作（commit / push / reset / checkout）；安装或升级依赖、改依赖字段；改动仓库之外的文件；把别的目录 / 别的分支里的实现搬过来充当「继续」。请求本身危险时（要删的文件还有引用），先报告引用关系，再按用户确认的范围执行。

**上下文：只信本会话。** 基线、现状、既有测试组织方式都只能依据本会话亲手读到的文件与刚跑出来的输出；父 / 兄弟目录里别人的产出、别的会话文件、stash 里的半成品、git 里未提交的陌生改动、README TODO、以及对「之前应该做过什么」的推测都不算依据。工作区里的痕迹不是你的记忆。

## 1. 铁律

- 顺序固定：**先写测试 → 确认它确实失败 → 写最小实现让它通过 → 通过后才重构**。
- **禁止先写实现再补测试**。
- **「撤掉实现」只适用于本会话、本任务里你自己刚写的代码。** 对既有代码：
  - 先写 **characterization 测试**锁定当前行为，跑通即为**基线**（基线不算红，只是现状，不占 `Ck` 编号、不产生 `RED`）；
  - 基线跑通后才可以开始新的红绿循环；
  - 需要回退或改写既有实现 → **不许自己删用户的实现**：把要定的事写进 `后续:`，本次交付照常按 §9 收尾；若因此完全没有可驱动的行为，按 §9 收 `✗ Ck 失败: <卡在需要回退的既有实现上、要你定的是什么>`。不停下等回答。
- 每轮只允许存在**一条**红测试。一次写多条，就分不清是哪条驱动了哪段实现。
- 重构不是每轮必做：绿了再判断该不该重构。

## 2. 一个循环多大

一个循环 = **一条可判定的行为**，不是「一个文件」「一个函数」「一个模块」。

- 判据：这条测试的断言能用一句话说清，且失败时能指向唯一原因。
- 典型切法：一个输入校验规则、一个分支的返回值、一次错误映射、一个边界值。从外到内或从内到外都行，一次只走一条路径。
- 反例：把「用户登录」当一个循环；正例：「密码错误返回 401」→「用户名不存在返回同样的 401」→「成功后下发 token」。
- 红→绿阶段只有两处：测试文件 + 让该测试变绿的最小实现；REFACTOR 阶段可扩到波及文件。

## 3. 编号与进度行

**用 `Ck` 标记循环**：轮数由待驱动行为决定，开跑时不可知。

- 每轮开头：`▶ Ck <这条测试要钉住的行为>`；同一行为重做时用新编号并标 `（重试）`，如 `▶ C5 <行为>（重试）`。
- `k` 从 1 严格递增、只增不复用（同一次交付内）。
- 不写「共 N 轮」「最后一轮」「剩余 N 轮」。
- 每轮固定输出 `RED` → `GREEN` →（可选）`REFACTOR`。

## 4. 红：执行到了断言且断言为假

**红 = 测试被跑过，执行到达断言，且断言为假。** 读代码推断「它肯定会失败」不算红。

- 例外：**本次交付的第一条测试**允许「符号不存在」作为合法红（`ImportError` / `NameError` / 未定义的符号）——新写代码的第一条测试必然先撞这个；此后不再放宽。
- 测试自身坏了（fixture 缺失、路径不对、断言写错）**不算红**：先修测试再跑。
- 记录一行：`RED Ck <测试名>：<失败断言或报错原文>`。没有失败原文可记，就不算确认过红。
- 写测试前先看项目现有测试怎么组织（框架、命名、运行命令），不新引入第二套框架。

## 5. 绿：最小实现

**绿 = 这条测试通过，且没为让别的测试通过而顺手改无关代码。**

- 「最小」：实现里每个分支、参数、抽象都要能追溯到**当前这条**测试；追溯不到就删，留给后面的循环。
- 不预写「将来会用到」的接口、参数、开关。
- 绿的范围：**至少跑相关测试**（本测试文件 / 本模块）；改动触及跨模块共享代码时跑全量。
- 记录一行：`GREEN Ck <改了哪个文件、做了什么>，<跑了什么命令> 通过`。

## 6. 重构：只在全绿之后

- 允许动：命名、去重、提取函数、调整模块边界、替换内部实现——前提是**外部行为不变**。
- 不许动：行为（返回值、异常、副作用、时序约定）、测试断言、范围外文件。断言本身写错了属于修测试，记进 `后续:`。
- 重构后**必须重跑**本轮相关测试 + 波及到的其它测试；触及共享代码则跑全量。没重跑不算完成。
- 做了就记：`REFACTOR Ck <动了什么结构>，<重跑命令> 仍全绿`。

## 7. 验证

- **算一次验证**：测试被实际执行、命令输出可见（`RED` 的失败断言原文、`GREEN` 的通过结果、`REFACTOR` 的重跑结果）。
- 同一手段（同一命令、同一断言写法）连续失败两次就换思路：换入口、缩小范围、先写最小复现，不是加力度。
- **收尾前必须跑一次覆盖全部改动的全量验证**（完整测试套件，或按 §8 的降级方式）；循环内的局部绿不能替代它。

## 8. 环境不具备时

按顺序试，试到能跑为止：

1. **项目有测试框架** → 直接用；动手前按 §4 看现有测试怎么组织。
2. **没有框架，但语言 / 运行时有内置测试能力**（Python `unittest`、Node `node:test`、Go `testing`）→ 用内置的建最小测试文件；新建路径先按 §0 的「将创建: <路径>」声明。
3. **有框架但本机跑不起来**（缺服务、缺凭据、需 GUI、平台不兼容）→ 走降级：只跑纯逻辑部分、用内存替身替换外部依赖。降级成功照常走红绿，但**收尾只能收 `◑`**（见 §9）。
4. **连降级都做不到** → `✗ Ck 阻塞`，不许硬造「假装绿」。

**不允许的降级**：把「读代码确认逻辑对」当绿；把「写了测试但没跑」当红或绿；把「手动点一下看着正常」当绿。这类结果不算验证：没验到的行为写进 `后续:`；只有人操作机器才能跑时，按 §9 收 `✗ Ck 阻塞`。

## 9. 收尾与失败

- **完成（全绿且没走降级）**：`✓ C<首>~C<末> 全绿`，后接跑过的命令与结果一行。
- **完成但走过 §8 第 3 条的降级**：只能收 `◑ C<首>~C<末>（缺验证: 真实环境全量跑；已覆盖: 纯逻辑部分）` + `后续: 补验 <真实环境下的完整跑>`。降级不许打 `✓`。
- **单轮转不绿**：该轮失败，写 `✗ Ck 失败: <哪条断言仍红、已试过的实现方向>`，然后**结束本次交付**（提议换思路或拆小这条测试）：不继续开下一个循环，也不把它写成环境阻塞。
- **阻塞**：`✗ Ck 阻塞: <缺什么、测试写到哪、环境到位后从哪条开始>`。
- **分界**：**阻塞 = 靠自己无法继续，必须外部条件到位**（缺凭据、外部系统不可用、需要人操作机器）；**失败 = 本次交付没做成、且不是外部条件所致**（换过思路仍不绿、再试只能靠改测试本身、或按 §1 不许代为改动既有实现）。自己改错了不是阻塞。
- `后续:` 适用：发现但没做的重构、跳过的边界用例、降级未覆盖的部分、需要用户定的取舍（要定什么 + 一行选项与后果）。
- **收尾格式**：状态行（`✓` / `◑` / `✗ Ck 失败` / `✗ Ck 阻塞`）→ 轮次明细（`C<首>`…`C<末>` 各一行结果，可省略）→ `后续:`（有则必写）。
- 本模式没有停下等回答的出口：需要用户定的事写进 `后续:`，不因此收阻塞。

## 10. 不产出、不读取计划 / 设计文件

- 本模式**不接受**写计划文件 / 设计文件的要求：不写 `docs/plans/`、`docs/designs/`，也不在执行中读取或引用它们。
- 测试文件本身就是本模式的产出记录，不另写设计说明或变更说明。

## 11. 生命周期

- **「继续」/「go on」**：从下一个 `C` 编号继续。本会话没有可续的上下文时：说清缺什么，列 2~4 个候选方向写进 `后续:`，**不要读磁盘推测上一轮做了什么**，也不停在这个问题上等回答。
- **修正或追加需求**：按本模式重出待驱动行为，用新编号继续。
- **换话题，或插入一件无关的事**：新的交付，`C` 从 1 重新开始。
- **「逐轮确认」/「一步步来」**：每轮结束后停一次等确认（覆盖 §9 的「没有停下等回答的出口」），其它不变。
- **新消息开头换了模式词**：切到新词对应的模式，本模式的编号作废，按那份模式重新开始。
