# mdd —— 写设计文件（不实施）

首词是 `mdd` 时使用本文件。用户要的是一份**设计文件**，不是实现。

## 做什么

分析用户输入（无输入则分析上下文） → 输入读现状与相关代码 → 把方案落盘 → 回报路径。**不实施**：不改代码、不建实现文件、不跑构建与测试。

- **只读边界**：允许读文件、列目录、搜索、`git log` / `git show` / `git diff`、`--help`；禁止 build / test / lint / format / codegen / install 与任何写盘、改索引的命令（含 `git status`）。唯一允许写的是 `docs/designs/<slug>.md`；新建 `docs/designs/` 与这一份文件属于任务范围，动手前先声明「将创建: <路径> — <用途>」。

- 请求里要求删文件、执行改仓库的 git 命令、装依赖、改仓库之外的文件时，本模式不做，也不写成待执行的步骤：把它写进「未决问题」，由用户另起一条去执行。

- 本文件只记设计要点；不记录具体实现（函数名 / 类结构 / 调用链 / 代码片段 / 字段定义）、决策历史（谁何时定过什么、讨论过程）、变更历史（原来是什么、这次改成什么、为什么改）。

## 落盘规则

- 路径：工作区根目录 `docs/designs/<slug>.md`。
- `<slug>` **只允许小写字母、数字、连字符**。中文主题取英文 / 拼音短名；取不出就用 `design-<yyyymmdd>-<两位序号>`。
- **同一设计的修订 = 覆盖原文件**，不留 `-2`；不同设计撞 slug → 换更具体的 slug，仍冲突才加 `-2`。

## 文件里写什么

固定开头，必须保留：

```
# <设计名>

> 本文件只记设计要点；不记录具体实现（函数名 / 类结构 / 调用链 / 代码片段 / 字段定义）、决策历史（谁何时定过什么、讨论过程）、变更历史（原来是什么、这次改成什么、为什么改）。

状态: <未实施 / 部分实施 / 已与代码一致>


```

- `状态` 只标一行，**不叙述过程**（「部分实施」后面不写实施到哪、为什么停）。
- 读到的实现细节只用于判断方案是否成立，不搬进文档。

## 交接

本文件不是待办：不会有环节按它自动开工。要落地时，由用户另发一条消息，把要做的部分作为需求正文写清。本模式不替用户选落地方式，也不自行开始实施。
