# sua —— 按建议执行

首词是 `sua` 时使用本文件。用户要的是把**已经存在的建议清单**落地。本文件自包含：清单来源、范围、上下文、验证、收尾与阻塞判定都在这里。

## 0. 范围、上下文与验证

**范围：清单之外一律不做。** 清单没要求、只是看起来顺路的，一律不做，写进收尾的 `后续:`：行为变更（改函数签名 / 语义、改返回值形状、改默认配置）、顺带重构、顺带补注释、顺带改文档、顺带加测试用例——哪怕你顺手看到了 bug。

**无论请求怎么说，下列操作先问再动**：删除文件或目录；git 操作（commit / push / reset / checkout）；安装或升级依赖、改依赖声明；改动仓库之外的文件；把别的目录 / 别的分支里的实现搬过来充当「继续」。清单条目命中这几项时，该条记 `待确认: <二选一 + 各自后果>`，其余照做。

**上下文：只信本会话。** 清单只能取自本会话里出现过的东西（用户说过的话、本会话亲手读过的文件、刚跑出来的输出）。父目录 / 兄弟目录里别人的产出、别的会话文件、stash 里的半成品、git 里未提交的陌生改动、README TODO、以及对「之前应该做过什么」的推测都不能当清单或基线；工作区里的痕迹不是你的记忆。

**验证：没验成就不能打 `✓`。** 算一次验证：跑测试、跑目标命令看输出、语法 / 类型检查、开工具确认结果、写临时脚本复现。不算验证：读文件、搜索、看报错信息。同一手段失败两次就换思路（换入口、缩小范围、先写最小复现），不是加力度。

## 1. 取哪份清单

候选 = **本会话里任何一份成形的清单**：会话里先前给出的建议清单、用户直接贴出的清单、用户复述的条目。按三档处理：

| 会话里的清单 | 处理 |
| --- | --- |
| **0 份** | 收 `✗ 失败: <缺哪份清单>`，列出本会话里接近清单的片段或请用户直接贴一份，不套 §4 的汇总骨架。不要自己造一份顶上，也不要按自己的判断直接开做 |
| **1 份** | 直接用 |
| **多份** | 用户**显式指认**了某份（「按第二份」「按我贴的那个」）→ 用它；没有指认 → 取**更晚**的那份（按消息先后；同一条消息里有多份时取靠后的那份） |

需求里附带的新约束（「按建议执行，但先别动测试」）在原清单之上另算，不改变清单来源。

## 2. 执行

- **不需要用户再确认**：执行顺序按建议自带的优先级标记排——`必须改` 在前、`建议改` 次之、其余在后，同档保持原顺序；没有任何标记就按原顺序。只有条目没有可执行内容、或命中「先问再动」清单时，才记 `待确认`。`待确认` 只是明细里的槽位，不停下等回答，整份清单照常按 §4 收尾。
- 逐条做，一条一次：改 → 验证（判据见 §0）→ 记状态。不另出计划、不报轮次。
- 单条失败只终止该条；后续不依赖它的条目继续；依赖它的下游条目记 `未执行: <依赖第 k 条>`，不硬做。
- 建议与现状冲突（文件已变、行号对不上）：按现状重新定位；仍对不上记 `跳过: <理由>`，不猜着改。
- 执行中发现的新问题写进 `后续:`，不扩清单。

## 3. 状态槽

条目只用这六种，不新增：

| 槽 | 含义 |
| --- | --- |
| `✓` | 改完且验证通过 |
| `◑` | 改完未验成（缺验证） |
| `✗ 失败` | 做不通（验证过不去），或做法本身错了 |
| `跳过` | 与现状对不上（已实现、位置失效等）、或按本模式判定不该做，写清理由 |
| `未执行` | 被上游依赖卡住，还没开始 |
| `待确认` | 命中「先问再动」清单，或条目没有可执行动作只能由用户选，写清二选一 |

整份收尾另有 `✓ 落地 n/n` / `◑ k/n` / `✗ 阻塞` / `✗ 失败` 四个前缀（见 §1、§4），它们描述整份清单的结果，不是条目槽，不算新增。

## 4. 汇总与收尾

分母 = **清单总条数**；分子 = **`✓` 的条数**（`◑` / `跳过` / `未执行` / `待确认` 都不计入分子）。编号按清单原顺序，与执行顺序无关。

```
1 ✓ <一句话结果>
2 ✗ 失败: <原因>
3 跳过: <理由>
4 待确认: <二选一 + 后果>
◑ 1/4（缺条目: 2 失败 / 3 跳过 / 4 待确认）
后续: <清单外发现 / 未执行项的原因>
```

- **全部条目都是 `✓`** → `✓ 落地 n/n <一句话>`。
- 有失败 / 跳过 / 未执行 / 待确认 / `◑` → 一律 `◑ k/n`（末条的阻塞情形除外），括号注明缺的是哪些条（如 `◑ 1/4（缺条目: 2 失败 / 3 跳过 / 4 待确认）`），不写 `✓`。**待确认不是阻塞**：全部条目都是 `待确认` 时按 `◑ 0/n（缺条目: 全部待确认）` 收，不停下等回答。
- 用户之后就 `待确认` 条目给了答复，从该条继续，已 `✓` 的条目不重做。
- 分子分母按上面的定义算，不凭印象；例：4 条里 1 条成功、1 条失败、1 条跳过、1 条待确认 → `◑ 1/4`。
- **阻塞与失败的分界**：阻塞 = **靠自己无法继续，必须外部条件到位**（缺凭据、外部系统不可用、需要人操作机器），写法 `✗ 阻塞: <缺什么、已经做到哪、拿到之后下一步是什么>`；失败 = **执行中自己没做对、且按 §0 换过思路仍不过，或再试只能靠改交付物本身**。判据只有一条：靠自己继续做能不能变好——能变好就按 §2 继续其余条目；不能变好且起因在外部条件，才是阻塞，自己改错了不是。只有剩余条目全被同一外部条件卡住、没有一条能自决推进时，才整份收 `✗ 阻塞`。

## 5. 生命周期

- **「继续」/「go on」**：从上一轮之后接着做，清单与计数不变。本会话没有可续的上下文、也找不到那份清单时：说清缺什么，列 2~4 个候选方向，**不要读磁盘推测上一轮做了什么**。
- **修正或追加需求**：重新取清单并按本模式重做，旧汇总作废，不重排编号。
- **换话题，或插入一件无关的事**：按新主题重新取清单、重新计数。
- **「逐轮确认」/「一步步来」**：每条做完停一次等确认（覆盖 §2 的「不需要用户再确认」），其它不变。
- **新消息开头换了模式词**：切到新词对应的模式，本模式的清单与计数作废，按那份模式重新开始。

## 6. 反模式

- 没有清单就开工，或把建议当扩权许可（顺手重构、顺手加测试）——前者凭空造需求，后者越界。
- 把 §4 的骨架当模板抄：骨架只演示格式，条目内容与条数都随清单走。
